# PM 产品目标 — 记忆系统 第一轮迭代

**撰写日期**: 2026-04-12
**作者角色**: 人类认知学专家 & 产品经理
**基于测试基线**: 2026-04-11 ~ 2026-04-12，50 样本，MSC 数据集

---

## 一、写在前面：我们在做什么？

我们不是在建一个聪明的数据库，我们在给 AI 装上人类记忆的工作方式。

人类的记忆不是检索引擎。你的朋友记得你上次说"最近很累"，不是因为他查了日志，而是因为那句话让他担心你——下次见面他会先问一句"最近好些了吗？"。这才是记忆的价值：它改变了关系的温度。

所以这个项目的成功标准只有一个：**用户感受到"这个 AI 记得我"**。

## 三、产品目标（用户语言）

### 目标 1：让 AI 真的"记住"用户，而不只是"拿到"记忆

**现状**：系统能召回 80% 的记忆数据，但 LLM Judge 显示只有 20% 的情况下记忆被实际用于回复。
召回了却没用，等于没记住。

**目标**：当用户说"我最近在学吉他"，下次对话 AI 要能说"上次你说在学吉他，有进展了吗？"，
而不是重复一句"哦，你在学吉他啊。"

**成功标准**：LLM Judge Memory Usage 从 0.20 提升到 0.45 以上。

---

### 目标 2：AI 不能沉默，也不能说废话

**现状**：
- 无记忆时，旧版 QA 直接拒绝回复（"I don't have enough information"）。
- 有记忆时，回复往往是重复用户原话或加几个 emoji 了事。

**目标**：无论有无记忆，AI 都要像一个善于倾听的朋友——有记忆时自然融入，无记忆时真诚好奇。

**成功标准**：Judge: Dialogue Quality 保持 ≥ 0.75，消灭所有"拒绝回复"输出。

---

### 目标 3：控制回复长度，说到点子上

**现状**：参考回复平均 21.9 词，系统回复 23.6 词，长度已经接近，但内容质量不达标。
（注：旧版长达 41 词，已有改善）

**目标**：简洁有力，15-25 词内完成有温度的回复，不堆砌表情符号，不说废话。

## 五、本轮不做什么（范围边界）

明确 **不在** 本轮范围内的事情，防止范围蔓延：

1. **不优化向量检索算法**（bge-m3 召回已够用，Memory Coverage 80% 可接受）
2. **不重构存储架构**（数据库和向量存储层不动）
3. **不扩大测试集规模**（保持 50 样本，优先质量而非规模）
4. **不新增多语言支持**（英文优先）
5. **不做实时记忆更新**（当前批量提取模式不变）
6. **不部署新的 embedding 模型**（bge-m3 保持不变）
7. **不修改 Memory Coverage 的召回逻辑**（召回管道表现已可接受）

## 六、优先解决的 1-2 个问题

### 问题 #1（最高优先级）：Prompt 没有强制要求 LLM 使用记忆

**现象**：Memory Usage = 0.20，召回了记忆但 80% 情况下没用上。

**根本原因**：`qa_module.py` 的 prompt 只是把记忆放在上下文里，说"可以用也可以不用"。
对于 LLM 来说，如果记忆和用户当前消息关联不紧密，它会选择忽略记忆。

**应对策略**（给 Dev 的方向，不是要求）：
- Prompt 改造：**强制要求** LLM 在回复中融入至少一个记忆事实，且要以自然方式而非背诵方式呈现
- 加入 few-shot 示例，展示"有记忆时的正确回复格式"
- 记忆注入部分增加"为什么这段记忆相关"的解释，帮助 LLM 理解记忆的关联性

**验证方法**：LLM Judge Memory Usage 是否从 0.20 提升至 ≥ 0.45

---

### 问题 #2（次高优先级）：记忆融合方式——背诵 vs. 对话

**现象**：有记忆时，AI 说"你之前说你有三个孩子，对吗？"——这是背诵，不是对话。

**认知学视角**：
人类在对话中激活记忆的方式是隐式的。你不会对朋友说"你上次告诉我你喜欢跑步"，
你会说"明天有比赛，你跑步应该能适应这个强度吧？"——记忆被自然地融进当下语境。

**应对策略（给 Dev 的方向）**：
- Prompt 中区分两种记忆使用方式：
  - 低质量（禁止）："You mentioned you have three kids."
  - 高质量（目标）："Sounds exhausting! Three kids at home must keep you busy—hope you got some rest."
- 加入反例示范（negative example prompting）

## 七、关于 BLEU 指标的 PM 立场

### BLEU 的本质问题

BLEU 是一个为机器翻译设计的指标，测量"生成文本与参考文本有多少 n-gram 重叠"。

在翻译任务中，"正确答案"是确定的——"我爱你"就该翻译成"I love you"，用 BLEU 合理。

但在**开放式对话**中，同一个用户输入可以有几十种同样优秀的回复：

```
用户: "我今天跑了 10 公里！"

参考回复: "That's amazing! You must be exhausted."
系统回复: "Wow, 10K is no joke! How are your legs feeling?"
```

这两个回复质量相当，但 BLEU 几乎是 0——因为词汇重叠极少。

### 当前 BLEU 极低（0.0078）的真实解释

不完全是系统质量差，而是：
1. 开放式对话的词汇多样性天然导致低 BLEU
2. 参考回复是 MSC 数据集中的真实人类对话，风格多变
3. LLM 生成倾向于副词、修饰语等 BLEU 不友好的表达

### PM 的指标建议

**保留 BLEU**（作为历史基线对比参考，不作为核心 KPI）：
- 优点：计算快，可复现，便于与学术工作横向对比
- 缺点：严重低估语义等价回复的质量

**新增/强化以下指标作为核心 KPI**：

| 指标                    | 类型         | 理由                                                      | 优先级 |
|-------------------------|--------------|-----------------------------------------------------------|--------|
| **LLM Judge Memory Usage** | AI 评测   | 直接衡量"记忆是否被正确使用"，最贴近产品目标             | ⭐⭐⭐⭐⭐ |
| **Semantic Similarity**    | 嵌入模型  | 语义相似度，不依赖词汇匹配，能识别同义表达               | ⭐⭐⭐⭐  |
| **LLM Judge Dialogue Quality** | AI 评测 | 衡量对话自然度，防止为了提分牺牲可读性                 | ⭐⭐⭐⭐  |
| **Memory Coverage**        | 系统指标  | 召回管道健康度，基础 KPI                                  | ⭐⭐⭐   |
| **BLEU / ROUGE**           | 词重叠    | 历史参考，不作决策依据                                    | ⭐      |

### 一句话结论

> **BLEU 是体温计，不是 CT 扫描。它告诉你有没有发烧，但判断不了是什么病。
> 当前系统的真正问题是"记忆没有被用上"，而这只有 LLM Judge 能发现。**
