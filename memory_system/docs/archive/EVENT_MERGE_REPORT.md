# 事件合并功能测试报告

## 功能概述

将事件合并逻辑从关键词匹配升级为 LLM 语义判断，解决"去打游戏"+"叫上小刘"+"打配合"被识别为 3 个独立事件的问题。

## 实现方案

### 1. 新增模块

**`llm/skills/event_merge_judge.py`**
- 函数：`should_merge_events(new_summary, new_participants, existing_summary, existing_participants)`
- 返回：`(bool, str)` - 是否合并 + 原因
- 模型：`settings.effective_fast_model` (Haiku)
- 超时：150 tokens

### 2. 集成位置

**`chat.py:252-277`**
- 原逻辑：`action + participant_ids` 关键词匹配
- 新逻辑：遍历当天所有事件，调用 LLM 逐一判断
- 触发时机：每次用户消息被识别为 `type="event"` 后立即执行

### 3. 合并规则（Prompt）

**合并条件**（满足任一即合并）：
1. 同一活动的不同描述：去打游戏+叫上小刘+打配合
2. 同一活动的细节补充：看电影+电影很好看、画画+画了一只猫
3. 泛指→具体：玩→玩游戏、学习→做数学题、运动→跑步
4. 计划→执行（同一天内）：准备去游泳→去游泳、想学钢琴→开始学钢琴

**不合并条件**（优先级更高）：
1. 完全不同的活动：打篮球 vs 做作业
2. 不同时段：早上跑步 vs 下午跑步
3. 不同地点：在教室画画 vs 在家画画
4. 冲突→和解：吵架 vs 和好（两个独立事件）
5. 问题→解决（涉及不同人）：摔倒 vs 小丽扶起、迷路 vs 警察送回家
6. 行为→反应：打碎碗 vs 妈妈没生气

## 测试方案

### 测试文件
`tests/test_event_merge_100.py`

### 测试覆盖
- **1-10**：同一活动不同描述（应合并）
- **11-20**：完全不同活动（不应合并）
- **21-30**：冲突→和解（不应合并）
- **31-40**：计划→执行→结果（应合并）
- **41-50**：多人活动不同视角（应合并）
- **51-60**：时间跨度（不应合并）
- **61-70**：情绪变化（混合）
- **71-80**：因果关系（应合并）
- **81-90**：地点变化（不应合并）
- **91-100**：边界情况（泛指→具体）

### 测试结果

#### 第一轮（初始 Prompt）
- 准确率：**68.0%**
- 目标：≥ 85%
- 状态：❌ 未通过

**主要问题**：
1. 计划→执行判断不稳定（有时合并有时不合并）
2. 因果关系过度合并（摔倒→被扶起 应分开但被合并）
3. 泛指→具体未识别（学习→做数学题 应合并但未合并）

#### 第二轮（优化 Prompt）
- 状态：测试中...
- 优化点：
  - 明确列出合并规则和不合并规则
  - 不合并规则优先级更高
  - 增加泛指→具体的明确规则
  - 强调问题→解决（涉及不同人）应分开

## 性能影响

### 调用频率
- 每条用户消息（type=event）触发 1 次
- 如果当天已有 N 条事件，需调用 N 次 LLM（最坏情况）
- 平均：1-3 次/消息

### 响应时间
- 单次 LLM 调用：~200-500ms (Haiku)
- 最坏情况（10 条事件）：~2-5s
- 优化方案：可考虑批量判断或缓存

## 后续优化方向

1. **批量判断**：一次 LLM 调用判断多个候选事件
2. **缓存机制**：相似事件对的判断结果缓存
3. **规则前置**：明显不同的事件（不同时段/地点）跳过 LLM
4. **Prompt 迭代**：根据失败用例持续优化规则

## 使用示例

```python
# 用户对话
用户: "去打游戏"           # → 插入 event_1
用户: "叫上小刘"           # → LLM 判断：合并到 event_1
用户: "打配合"             # → LLM 判断：合并到 event_1
用户: "晚上做作业"         # → LLM 判断：不同活动，插入 event_2

# 最终结果
event_1: "去打游戏；叫上小刘；打配合"
event_2: "晚上做作业"
```
